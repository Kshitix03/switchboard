# Decisions Log

## 2026-07-28 — Project setup

- **Chosen:** Qdrant in embedded/in-memory mode (`QdrantClient(":memory:")`) instead of Docker Compose.
  **Rejected:** docker-compose'd Qdrant service (PRD default).
  **Why:** No Docker dependency needed for a 2-day build; keeps the dev loop fast. Trade-off: the vector index does not persist across process restarts, so `index.py` re-embeds on every run. Mitigated by caching embeddings to disk separately from the Qdrant collection, so re-runs are cheap even though the DB itself is ephemeral.

- **Chosen:** PayPal's public OpenAPI specs (ingest_openapi.py) instead of a Postman collection.
  **Rejected:** ingest_postman.py as the primary path (still may add later if a collection shows up).
  **Why:** No Postman collection file on hand; PayPal publishes REST OpenAPI specs on GitHub covering Invoicing, Payments, Orders, Disputes, etc. — enough surface area for the real 50-tool base.

- **Chosen:** Gemini for LLM calls (planning, fill/validate, utterance generation) and Gemini Embedding for embeddings.
  **Rejected:** OpenAI embeddings + a different LLM provider, all-one-vendor + local sentence-transformers.
  **Why:** User has live Gemini quota; single provider simplifies key management.

## 2026-07-28 — Phase 1: model availability, actual models used

- **Chosen:** `gemini-flash-latest` instead of `gemini-2.5-flash` for utterance generation.
  **Why:** `gemini-2.5-flash` and `gemini-2.5-flash-lite` are listed by `models.list()` and show quota in the console, but both 404 with "no longer available to new users" on actual `generateContent` calls -- a console/API mismatch on this account. `gemini-2.0-flash` hit a 429 quota-exhausted, `gemini-3.5-flash` hit a transient 503. `gemini-flash-latest` (an alias Google keeps pointed at a current, non-deprecated Flash model) worked cleanly and is the safer long-term choice since it won't rot the same way a dated model id will.

- **Chosen:** `gemini-embedding-001` for embeddings (3072-dim output), used as-is with cosine distance in Qdrant.
  **Why:** Confirmed working via a direct test call; `gemini-embedding-2` also works but `-001` is the more established/stable of the two.

- **Chosen:** Isolated `.venv` inside `switchboard/` for all Python dependencies, installed via `python -m venv .venv` + `.venv/Scripts/python.exe -m pip install -e .`.
  **Rejected:** global `pip install -e .` (tried first).
  **Why:** A global `pip install --user -e .` upgraded the system-wide `websockets` package (16.0 -> 15.0.1 due to a dependency resolution step), which broke two unrelated pre-existing global packages (`alpaca-trade-api`, `polygon-api-client`) that pin `websockets<13`/`<11`. Restored global `websockets` to its original 16.0 and uninstalled all switchboard-related packages from the global user site-packages, then rebuilt everything inside `.venv` so this project can never again touch global state. Lesson: always use an isolated environment for a new project on a shared machine, even for a quick build.

- **Batching for utterance generation:** 8 tools/call to stay well under the account's 20 RPD limit on Flash-tier models (9 calls for 70 tools). Embeddings batched at 10 texts/call (comfortably under the ~30K TPM cap for card-text-sized inputs). Both cache to disk keyed by content hash so reruns after the first cost zero calls.

## 2026-07-28 — Phase 2: router

- **Chosen:** `cross-encoder/ms-marco-MiniLM-L-6-v2` (local, via `sentence-transformers`) for reranking, run entirely offline after first download.
  **Rejected:** using Gemini itself for reranking.
  **Why:** rerank runs on every query, and the benchmark (Phase 7) will run 50-60 golden queries x 3 registry sizes x 3 arms -- that volume would exceed the account's tight Flash-tier RPD budget almost immediately. A local cross-encoder has no rate limit and matches PRD section 14's framing of an off-the-shelf, untuned reranker.

- **Shared retrieval path:** `routing/store.py` lazily builds/caches records, the in-memory Qdrant client, and the BM25 index once per process. `dense.py`, `sparse.py`, and `router.py` all read through it, so `system_search` (Phase 5) can reuse the identical path with zero duplicated retrieval code, per PRD section 4.2.

- **Smoke test result (10 hand-picked queries, PRD Phase 2 acceptance bar):** 10/10 correct tool ranked #1, including the two near-miss pairs tested (`payments.captures.refund` vs `invoicing.invoices.refunds` for "refund a captured payment" vs "record a manual refund on an invoice"; `invoicing.invoices.create` vs `invoicing.invoices.send`). No ingestion rework needed before moving to Phase 3.

## 2026-07-28 — Phase 4: graph and execution

- **Deferred Phase 3 (golden set)** at the user's request to build the graph/execution path first; the golden set still needs to be hand-written before Phase 7's benchmark can run.

- **Response schemas added to the schema store.** `ingest_openapi.py` now also bundles each operation's 2xx response schema (`response_body`, same `$ref`->`$defs` inlining as the request schema) so the mock executor can synthesize schema-shaped fake responses. Re-running ingestion cost zero extra LLM/embedding calls since `tools_enriched.json` and `embedding_cache.json` are keyed independently and untouched by this change.

- **Two-step fill instead of one combined "pick tool + fill args" call.** First tried a single call with a generic `{"tool_id": str, "args": object}` response_schema -- Gemini's structured decoding satisfied the loose `args: object` constraint with an empty `{}` every time, ignoring prose instructions to fill nested required fields. Splitting into (1) tool selection constrained to an enum of candidate ids, then (2) arg-filling using the *actual* tool's own flattened schema as `response_schema`, fixed this immediately: constrained decoding only works when the schema itself encodes the real structure, not when it's a generic passthrough object.

- **`graph/schema_utils.py` flattens bundled ($ref/$defs/allOf) schemas into an inlined shape for both the fill prompt and the `response_schema` constraint.** Two bugs found and fixed while wiring this up against PayPal's real (not toy) schemas:
  1. A depth counter that treats every `$ref` hop *and* every object-property traversal as "one level" hits real nesting fast (`invoice -> items -> item -> unit_amount -> money -> currency_code` is depth 9 from ref-chasing alone, not true business nesting). Original `MAX_DEPTH=8` silently truncated `currency_code` to a bare `{"type": "object"}` with no error -- a correctness bug, not a crash, so it was only caught by manually inspecting an interrupt payload. Settled on `MAX_DEPTH=14`.
  2. No breadth cap meant every optional property at every level got fully expanded recursively -- the real invoice schema (dozens of optional top-level fields, several deeply nested) ballooned to 40K+ characters, which the smaller Gemini model rejected outright (400 INVALID_ARGUMENT, no detail given) even though a larger model had accepted it once earlier. Added `MAX_OPTIONAL_PROPS=10` per object level (all required fields kept in full, optional fields capped) -- brought the same schema to ~32K chars and it now passes as a `response_schema` reliably. This is the kind of thing that only shows up against real-world schemas, not toy examples, and is worth naming explicitly as a scaling risk for Phase 7 (larger/more complex padded tools may need the same cap re-tuned).

- **Model swap under time pressure: `gemini-flash-latest` -> `gemini-flash-lite-latest`.** Mid-Phase-4 testing exhausted the 20 RPD free-tier quota on whatever model `gemini-flash-latest` currently resolves to (the 429 error revealed it as `gemini-3.6-flash`, quota shared across every call to that alias). Switched to `gemini-flash-lite-latest`, confirmed working, and is now the model for all graph LLM calls (plan/select/fill/observe/chat). Aliases were chosen over dated ids both times specifically so they don't rot, but the trade-off is upstream quota/routing changes can shift under us mid-session with zero warning -- worth budgeting slack time for this on a free-tier key.

- **Idempotency:** `tools/executor.py` derives a deterministic key from `sha256(trace_id:tool_id:sorted(args))`, so the same logical write always carries the same key across a graph retry/resume, per PRD section 7's "a retried 'send $50' that sends twice is the failure that actually matters."

- **Live execution is explicitly out of scope** (PRD cut list item 1). `executor.execute_live()` raises `NotImplementedError` with a message pointing at this decision, rather than silently no-op'ing or returning a fake success -- a caller can't mistake the stub for a real call.

- **Acceptance test passed** (`tests/test_graph_smoke.py`): "Create a draft invoice for $500 consulting work for jane@acme.com" in `--dry-run` mode prints the exact call (method, path, fully filled nested args) and never executes; in interactive mode it pauses at the approval gate (write-class, medium risk), and resuming with approval executes (mocked) and produces a natural confirmation message referencing the mock invoice id.

## 2026-07-28 — Phase 5: rag_search and system_search

- **Docs corpus sourced from the OpenAPI specs themselves, not developer.paypal.com.** The real PayPal docs site is a JS-rendered Redocly/Gatsby SPA -- `curl` (and WebFetch, which also just fetches then renders) get an empty shell, no real prose. Instead, `registry/ingest_docs.py` extracts `info.description` (API overview) and `tags[].description` (section descriptions) from the 8 specs already on disk -- this is real PayPal-authored text, just sourced from inside the spec files rather than the rendered site. Filtered to a 120-char minimum to land at 24 chunks, within the PRD's 20-30 target. Honesty flag: this is thinner than genuine narrative documentation (no workflow walkthroughs, no code samples) -- acceptable for the retrieval demo, but a real corpus would need actual doc pages.

- **rag_search is a normal registry entry** (`registry/add_internal_tools.py`), 71st `ToolRecord`, `domain=knowledge`, embedded into the same `tools` Qdrant collection -- it competes for retrieval slots exactly like every PayPal API tool. Re-running `index.py` after adding it only embedded the 1 new tool (70 were cache hits), confirming the content-hash cache works as designed.

- **Docs live in a second Qdrant collection (`docs`) on the same in-memory client instance** as the `tools` collection (`routing/store.py::ensure_docs_collection`), per PRD 4.2's "same Qdrant instance." `tools/rag_search.py` only searches this collection; it doesn't reuse the hybrid+rerank funnel -- a single dense pass over 24 short doc chunks doesn't need BM25/RRF/cross-encoder overhead the way 71+ tool cards do.

- **`execute_node` special-cases `tool_id == "rag_search"`** to run a real search instead of the mock-response generator every other (PayPal API) tool gets, and marks its result `status: "executed"` (not `"mocked"`) so downstream summaries and the trace log stay honest about what actually happened. Caught and fixed this after first observing `observe_node`'s prompt claim "(mock execution)" for a call that had, in fact, really run.

- **`system_search` is not a competing registry entry.** Per PRD 4.2 it's a second renderer over the identical `routing.router.retrieve()` call `retrieve_tools_node` uses -- invoked directly when `plan_node` classifies a turn as `"meta"`, not something that shows up in the 6-candidate funnel. It also answers "status of my last request" by reading a new minimal trace log (`observability/tracing.py`, one JSON line per executed tool call) -- a real (if narrow) trace store, seeded now so Phase 6 can expand it rather than build one from scratch.

- **Bug found and fixed: `plan_node` initially misrouted PayPal-specific conceptual questions to `"chat"`.** "How do refunds work on PayPal, conceptually?" was classified as generic chat and answered from the model's own training data, completely bypassing `rag_search` -- defeating the point of having PayPal-grounded docs retrieval. Reworded the plan prompt so "chat" is reserved for turns with *no* PayPal connection at all, and any PayPal-related question (conceptual or actionable) prefers `"retrieve_and_act"` so retrieval gets a chance to surface `rag_search` or the right API tool. After the fix, the same query correctly retrieves `rag_search` as the top candidate and answers grounded in the actual docs corpus (referencing the Payments/Disputes APIs by name).

- **Acceptance check (`tests/test_phase5_smoke.py`):** the refund-concept query selects and executes `rag_search`; "What tools do you have for handling invoices?" routes through `system_search` and lists real invoicing `ToolRecord`s by id/domain/summary; "What's the status of my last request?" reads the trace log and reports the last tool call correctly.

- **CORRECTION to an earlier entry in this log:** the first version of this section said the initial 16 queries were user hand-written. That was wrong -- the user later clarified explicitly: **"nothing is user authored, everything is AI-generated"**. - **This is a direct, disclosed deviation from PRD section 8.1** ("Write the 50 to 60 queries yourself. Do not generate them. Generated eval sets inherit the system's blind spots and an interviewer can smell it.") and from section 14's honesty flags, which ask the README to state the golden set is "hand written by one person." It is not. The README and report must say so plainly rather than imply otherwise -- see the honesty-flags update below. The real risk PRD 8.1 names is correlated blind spots: an AI generating both the routing system and its eval queries can unconsciously phrase queries in ways that system happens to handle well, understating how it performs against genuinely unpredictable human phrasing. That risk applies here and should be named in the final report as a limitation, not hidden.

- **Eval design quality is independently strong regardless of authorship** -- near-miss pairs/triples (`create_plan`/`create_subscription`; `suspend`/`cancel`/`activate` subscription; `authorize`/`capture_order`/`capture_authorization`; `update_plan_pricing`/`revise_subscription`; the `g033`/`g057` webhooks trap), needs-clarification cases with genuinely ambiguous phrasing (`g049` "stop the Ortiz subscription" -- ambiguous between suspend and cancel, which are not equally reversible), and knowledge-vs-action near misses (`g052`-`g055` overlapping vocabulary with real API tools) match what PRD 8.1 asks for structurally. Good design does not make it hand-written; both facts are stated here on purpose.

- **Added three domains to the registry to support queries as designed, rather than water them down:** `subscriptions` (16 tools, `billing_subscriptions_v1.json`) for g009-g011/g032/g035-g038/g042; `webhooks` (16 tools, `notifications_webhooks_v1.json`) for g033/g057, explicitly called "the best meta test in the file"; `tracking` (5 tools, `shipping_shipment_tracking_v1.json`) for g029. All three are the same official PayPal spec repo as everything else. Registry is now 108 tools (107 real PayPal + `rag_search`). Each addition only cost LLM/embedding calls for the new tools -- the content-hash caching held up across three incremental additions now.

- **Corrected all tool ids to match the actual registry.** Every query's tool id was illustrative (`paypal.reporting.list_transactions`, `paypal.invoicing.create_invoice`, `paypal.payments.get_order` -> actual `paypal.reporting.search.get`, `paypal.invoicing.invoices.create`, `paypal.payments.orders.get`, etc.), not the concrete `paypal.{domain}.{operationId}` ids the OpenAPI-derived registry actually uses. Two ids needed judgment calls rather than a 1:1 rename: g024's "cancel a sent invoice" maps to `paypal.invoicing.invoices.cancel` (the registry's `invoices.delete` is for drafts, `invoices.cancel` is specifically for sent invoices -- this is a real, already-present near-miss pair, not one I had to construct); g043's "set up a product" maps to `paypal.catalog.products.create` since PayPal's actual subscriptions API has no separate product-creation endpoint of its own -- Catalog Products is the real API products live in. - **`RESOLVE:`/`RELATIVE:` prefixes in `required_args`** (e.g. `RESOLVE:henderson_order`, `RELATIVE:last_month_start`) are intentional placeholders for entity/temporal resolution, not literal expected string values -- Phase 7's argument matcher needs to special-case these rather than exact-string-match them. Kept flat/logical argument shape (e.g. `"amount": 50` rather than the real nested `detail.currency_code`/`items[].unit_amount.value` structure) since that mirrors the PRD's own section 8.1 example exactly.

- **Retrieval sanity check** (router only, no LLM calls, to conserve the tight daily quota): 4 of 5 hardest near-miss queries from the original 16 retrieved the correct tool at top-1 (`plans.create`, `subscriptions.create`, `suspend`, `captures.refund`). The 5th (g008) top-1'd `disputes.get` over `disputes.list` -- a genuine ambiguity the query's own note already flags as acceptable either way, not a retrieval defect. Spot-checked 6 more from the new domains: `webhooks-event-types.list`, `invoices.cancel` (vs `.delete`), `plans.update-pricing-schemes`, and `subscriptions.revise` (present in top-6, but at a low, noisy margin -- a genuinely hard case, exactly as labeled) all behaved correctly or as-designed. The full 60 have not yet been run end-to-end through the graph (Phase 7 will do this properly as the actual benchmark).

- **Real finding, not a bug: PayPal's API has two legitimate ways to attach tracking to an order.** g029 ("add tracking ... to the Ferraro order") was authored expecting `paypal.tracking.trackers.post` (the dedicated Shipping Tracking API), but retrieval ranked `paypal.payments.orders.track.create` (the Orders API's own `/track` endpoint) higher. Updated g029's note to accept either rather than picking a single "correct" answer arbitrarily.

## 2026-07-29 — Phase 7: benchmark

- **Given the hybrid approach the user chose for the quota constraint** (see the question asked before starting this phase): the scaling chart's headline metrics are computed with zero LLM calls (embeddings + local cross-encoder only), run at full scale across all 46 scoreable golden queries x 3 registry sizes x 3 arms, plus a small real end-to-end sample (n=15, real Gemini calls, core tier only) to validate the zero-cost proxy against real model behavior. Full details and the numbers themselves are in `docs/RESULTS.md`; this entry covers the methodology decisions and what was found while building it.

- **Registry size tiers are 108/250/500, not the PRD's suggested 50/150/500** -- carried over from the Phase 3 decision that our real, unpadded registry already grew to 108 tools. All 108 real tools are present at every tier; only padding (from GitHub's public REST API OpenAPI spec, 1216 real operations, same-repo-pattern source as everything else, tagged `source="padding:github"`) grows underneath them.

- **Padding tools get no LLM enrichment** (empty utterances, keywords from path tokens only) -- deliberate, disclosed asymmetry: production tools got hand-tuned utterances because they're the surface actually built; incidental padding pulled in purely to inflate registry size doesn't warrant the same investment. This also avoided burning ~40 enrichment batches worth of quota on tools that exist only to be distractors.

- **A real, load-bearing bug found in the metric design itself, not just the data:** the first version of "full-binding accuracy" was defined as "is the expected tool the single nearest embedding neighbor across the whole registry (no top-k cutoff)." This is mathematically IDENTICAL to dense-only's top-1 pick -- nearest-neighbor-of-1 cannot change based on how many additional results you also retrieve. So the metric literally could not distinguish arm A from arm B by construction, and the initial benchmark run produced identical top1_accuracy=0.52 for both across all three sizes -- which looked like a real result until the math was checked. Full binding's true distinguishing failure mode (an LLM's attention/context degradation when given hundreds of tool schemas at once) is not a retrieval-ranking phenomenon at all and can't be approximated this way. Fixed by dropping the fabricated "accuracy" comparison for arm A entirely and reporting only what's real for it: prompt size, which grows from ~413K to ~642K characters as the registry scales 108->500, while B and C stay flat at ~17-29K. That flat-vs-growing prompt-size chart is the actual, honest version of "the one image that answers the question" -- not a per-arm accuracy curve.

- **The real validation sample (n=15, core tier) surfaced that the zero-cost retrieval proxy underestimates true accuracy substantially:** proxy (top-1 after hybrid+rerank) scored 0.47, but the real end-to-end call through the actual `graph.nodes._select_tool` code path scored 0.73 on the same 15 queries -- a 26-point gap. Agreement between the proxy's pick and the real pick was only 0.60. The LLM's own reasoning, given the same 6 retrieved candidates, recovers from several retrieval ranking mistakes (e.g. g002, g008, g012, g017 were proxy-wrong but real-correct). This is reported explicitly as "the proxy is a conservative lower bound, not a faithful accuracy estimate" in `docs/RESULTS.md`, rather than letting a reader assume the zero-cost numbers represent true system accuracy.

- **Real finding: hybrid+rerank recalls the correct tool LESS often than dense-only alone**, at every registry size (0.72 vs 0.83 at 108 tools; 0.70 vs 0.80 at 500) -- the opposite of what the production design assumes. Investigated by hand rather than accepted blindly: spot-checked 6 concrete cases (g013, g018, g020, g041, g042, g053) where dense-only's top-6 contained the correct tool but hybrid+rerank's top-6 didn't. The pattern is consistent: `cross-encoder/ms-marco-MiniLM-L-6-v2` (trained on general web query-passage relevance, not this domain) appears biased toward tool cards that read as direct action fulfillment over list/read/knowledge tool cards -- in g042 and g053 specifically, the reranker dropped the correct `plans.list`/`rag_search` entirely in favor of action-sounding neighbors that BM25's fusion pulled into the candidate pool. This is a real, disclosed cost of the "off the shelf, not tuned" reranker choice named back in Phase 2 -- now shown concretely with real examples rather than left as an abstract caveat. It does not invalidate the design (recall@6 for hybrid+rerank, while lower than dense-only, is still well above the trivial floor, and the real validation sample shows the downstream LLM call still often recovers from an imperfect top-6), but it's a legitimate weakness worth naming per PRD section 13.

- **Discovered via the validation sample, not fixed silently:** g014 ("how long do buyers have to open a dispute after paying") should route to `rag_search` per the system's own knowledge-routing design, but both the retrieval proxy and the real LLM call picked `paypal.disputes.disputes.list` instead. This is exactly the knowledge-vs-action confusion category the golden set's g052-g056 were designed to probe, now confirmed as a real, live failure rather than a hypothetical one. Left unfixed for this build (disclosed in the report) rather than special-cased away.

- **Chart follows the dataviz skill's method:** two separate single-metric charts (prompt size, recall@6) rather than one dual-axis chart combining unlike scales; fixed categorical color order (palette slots 1-3: blue/orange/aqua, which validate all-pairs CVD-safety in both light and dark modes per the skill's reference palette) assigned by arm identity, not by rank; log scale for the prompt-size y-axis given the ~35x range between arms.

## 2026-07-28 — Phase 6: observability (Phoenix)

- **Phoenix over LangSmith**, per PRD section 12, exactly as planned: open source, OTel native, runs locally via `arize-phoenix` + `arize-phoenix-otel`. `observability/otel.py` registers a TracerProvider (`phoenix.otel.register`) and every graph node is wrapped with a `@traced_node()` decorator that opens a span per node call -- latency is automatic (span duration), no manual timing code needed.

- **Span attributes capture exactly what PRD Phase 6 asks for:** `retrieve_tools_node` records dense/sparse/fused/reranked candidate ids at every funnel stage (`record_funnel`) plus final scores; every LLM-calling node (`plan`, `chat`, the two calls inside `fill`, `observe`) records prompt/completion/total token counts (`record_tokens`, reading Gemini's `usage_metadata`); `fill_node` records the selected tool; `validate_node` records `retry_count` and validation errors. One retry loop is directly visible in a captured trace as two `fill_node`/`validate_node` span pairs.

- **`GraphInterrupt` (the approval gate pausing for a human) is explicitly not treated as an error span.** First pass caught it in the generic `except Exception` handler and would have marked every approval-gated write as a failed span -- normal control flow, not a defect. Fixed by catching `langgraph.errors.GraphInterrupt` first and tagging `graph.interrupted=True` instead of an error status.

- **Two real Windows-specific bugs found and fixed, both environment quirks rather than design flaws:**
  1. Phoenix's own success banner prints an emoji (`\U0001f30d`), which crashes on Windows' default cp1252 console encoding. Fixed by reconfiguring `sys.stdout`/`sys.stderr` to UTF-8 at the top of `cli.py`.
  2. Phoenix's default OTLP gRPC port (4317) collided with an unrelated pre-existing `jaeger-all-in-one.exe` process already running on this machine (not something this project started, so it was never touched or killed). Fixed by setting `PHOENIX_GRPC_PORT=4327` as a default (`os.environ.setdefault`, so a user's own configuration always wins) in `cli.py`.

- **A real bug in `observability/otel.py` itself, caught by testing rather than review:** `setup_tracing()` originally returned the `Tracer` object, not the `TracerProvider` -- looked correct at a glance since both come from the same `register()` call, but only the provider exposes `add_span_processor`. Fixed to track and return the provider (`get_tracer()` remains the accessor for the tracer used to open spans).

- **Acceptance check (`tests/test_phase6_smoke.py`):** launches Phoenix, runs the dry-run invoice-creation flow from Phase 4, and asserts on captured span content (not just "it didn't crash"): funnel ids present at every stage, token counts present on LLM-calling nodes, `tool.selected` present on `fill_node`. All passed. The trace is inspectable at the printed Phoenix URL (`http://localhost:6006`) for a human to open and narrate, per the PRD's actual acceptance bar for this phase.

- **The minimal JSONL trace log from Phase 5 (`observability/tracing.py`) is kept as-is, not replaced.** It answers "status of my last request" cheaply without needing to query Phoenix's storage; the OTel spans are the rich, per-node trace for debugging/narration. Two trace stores for two different consumers (a quick status lookup vs. a full inspectable trace) is intentional, not redundant.
